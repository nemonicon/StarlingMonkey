Enable the profile explicitly when building StarlingMonkey or its ComponentizeJS embedding:

cmake -S . -B cmake-build-node-profile -DCMAKE_BUILD_TYPE=Release \
  -DENABLE_BUILTIN_NODE_COMPAT=ON

The option defaults to OFF. Normal builds do not install these modules or global Buffer. The profile requires the existing text-codec builtin. Its hexadecimal kernels are native guest code; the overload/error/view semantics live in a small JavaScript facade. Neither module adds a host service or calls WASI directly. The final component import set still depends on the application world and ComponentizeJS feature selection, and must be inspected after composition.

Module and bundler contract

Native installation uses the existing add_builtin and api::Engine::define_builtin_module. Both node: and bare aliases are registered with the same exported values. Global Buffer is the same constructor as the module export. Namespace objects remain cached by specifier; aliases need not have equal namespace-object identity unless the bundler canonicalizes them.

In the core Buffer/stub modules, every named export equals the corresponding default-object member; their defaults and constants are frozen. Optional foundations have their own declared default graphs: Path/Querystring/StringDecoder defaults are mutable objects, Events/Assert defaults are mutable functions, and named bindings retain the initially registered references. There is no runtime CommonJS loader or syncBuiltinESMExports mutation protocol. Unknown names fail ESM linking; unadmitted modules have no implicit empty stub.

A bundler must preserve the selected native imports before an adapter plugin can replace them. The finite resolver in tests/node-compat/profile-bundler.mjs canonicalizes modules selected by the actual engine receipt, externalizes their node: imports, rejects other builtins/custom adapters, and lowers a deliberately narrow literal CommonJS require contract for local .cjs files imported by explicit path. It is not a general npm CommonJS package loader. Applications using Jco’s default Node adapter bundling do not automatically use this native profile. Global injection must use the canonical native Buffer and must not bring in another Buffer implementation.

node:child_process has nine callable exports plus default: ChildProcess, _forkChild, exec, execFile, execFileSync, execSync, fork, spawn and spawnSync. Calls and construction always throw an Error with code, module, operation and profile fields. This applies during snapshot initialization and deployed execution. Importing and inspecting the namespace/default object is safe; neither is an accidental thenable. No process-spawn or custom host capability is imported.

Native ownership and generated sources

The byte kernels allocate JS-managed typed arrays or owned staging memory. All JS objects/strings are rooted across allocation. Typed-data pointers are borrowed only inside no-GC regions, after allocation and validation, and never retained across a callback or suspension. Hex encoding copies owned staging bytes into a JS string. The production UTF8 encoder now writes directly into an exactly sized GC-owned Uint8Array; TextDecoder owns its UTF16 staging allocation and releases the borrowed input before result-string creation. These remain distinct paths, without a blanket zero-copy claim. No Rust/C++ allocation is implicitly transferred to an incompatible allocator.

Fresh, bounded outputs from captured native producers receive prototype and private WeakSet branding without reading their backing-buffer getter. This avoids materializing SpiderMonkey’s small inline arrays unnecessarily. External inputs and observable species/view outputs keep full validation. The allocation follow-up records the mechanism, matched experiment and limits.

The facade and stub sources and their versioned manifest live under builtins/node-compat. The checked-in generated factory header keeps normal CMake builds independent of Node/npm. The accompanying deterministic generator checks that the header agrees with those sources and validates the manifest against its versioned restricted schema. Factories execute as strict script in the content realm after native text codecs are installed, before application module evaluation.

NODE_COMPAT_GC_STRESS is a development-only build setting for forced collection at rooted kernel boundaries. It is not a Node API or host capability. It must not be enabled for performance measurements.
