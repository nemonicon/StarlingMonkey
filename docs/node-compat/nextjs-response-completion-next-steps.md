## Actual selected path and completion boundaries

1. **Next action/internal fetch.** The selected app's minified `app-page.runtime.prod.js` redirect function at byte 474049 performs an internal GET and, for the RSC content type, returns its `response.body` as a Flight result. Its Web-stream writer `K` at byte 451647 writes to the Node response, flushes when offered, respects `drain`, and on close calls `res.end()` and awaits the response `finish` promise. The alternate classic-readable writer is conditional; no trace here proves it selected request 7. V5's `installSignalPipeTo` requires the genuine global/native Web-stream constructors. With a signal, its normal close path awaits the final read and outstanding writes before closing the destination; without a signal it delegates to the original implementation. These are Source paths, not a per-request branch trace.

2. **Middleware/compressor.** `router-server.js` installs compression unless disabled and releases an unfinished compressor on premature response close. Its compiled middleware saves the original response methods, creates `zlib.createGzip`, forwards compressor `data` to the saved response `write`, pauses on false, resumes on response `drain`, and invokes the saved response `end` on compressor readable `end`. The wrapped `res.end()` ends the compressor first. Thus response headers, compressor writable `finish`, compressor readable `end`, bridge `finish`, and client HTTP completion are distinct events.

3. **Selected guest zlib/classic streams.** `register.cpp:380–412` supplies the real selected classic `Transform`, guest kernel and internal `nextTick` to the streaming factory. The generated factory contains the exact `stream-facade.mjs` body after its single export removal; its historical `UNCOMPILED` comment is not a build-status claim. Actual compile metadata includes `zlib/stream-kernel.cpp`. Facade `Compressor._flush` feeds `FINISH`; `pump` requires `ended` before completing that job, queues the returned bytes with `push`, and handles backpressure/read resumption. Kernel `pull` ends the codec on `Z_STREAM_END` after copying its final output into an owned JS array. The private handle is retired idempotently by `close`/finalizer. Classic `Transform.final` pushes readable EOF only after `_flush` succeeds; writable `finish` waits for pending callbacks. None of these files was changed by the six-file cleanup.

4. **Node message bridge.** `BridgeServerResponse._write` owns a copy before its callback and defers that callback under Web-stream backpressure. `_final` closes its Web-body controller before completing the writable callback; `_destroy` errors an unfinished body and releases a pending write. `createRequestBridge` intentionally returns the published Response while the handler Promise continues with an error handler. Therefore an HTTP status/Response object is not body completion, and the detached handler's lifetime must not be equated with export completion. The bridge is byte-identical to the earlier native/Node shared bridge; the classic-stream backend differs.

5. **V5 adapter and standard WASI.** Unchanged `guest-entry.mjs:505–640` awaits that Response, transfers it once with `ResponseOutparam.set`, reads its Web body to `done`, and writes every chunk through `blockingWriteAndFlush` in 4,096-byte slices. Only afterward does it drop the output-stream child and consume the outgoing body with `OutgoingBody.finish`. Catch/finally preserve the primary error, cancel/release the reader and avoid disposing a parent after uncertain child disposal. Successful outparam transfer is **not** successful body finish. The selected WIT requires the output-stream child to be gone before body finish; dropping an unfinished body denotes an incomplete/corrupt response. Adapter exceptions/drop are a separate unsuccessful terminal path, not evidence that a normal finish occurred.

6. **Native fetch is a different outgoing owner.** `RequestOrResponse::maybe_stream_body` can forward an unreified incoming native body using `HttpOutgoingBody::append`; `do_body_source_pull` has an identity-transform append optimization. `BodyAppendTask` still owns cached incoming/outgoing subscriptions and has no implemented cancellation. Its EOF callback/retirement and `BodyWriteAllTask` are deferred. `HttpOutgoingBody::close` flushes, drops its pollable/stream and calls the generated finish function, but still ignores that function's boolean/error result. This is a concrete preexisting error-reporting gap to test separately; V5's outer response uses imported JS WASI resources, so this audit does **not** identify that C++ close as the failed POST's outer finish path.

The cleanup covers ordinary native incoming-body read EOF/error and direct underlying-reader cancellation, plus exactly-once response-future retirement/Request-slot transfer. Per-chunk task retirement remains separate from terminal body disposal. Its sticky native-append exclusion deliberately prevents those new read cleanup hooks from dropping an append owner's subscriptions. It does not cover append completion/cancel, both-branch clone cancellation, unreified/post-header abort reason parity, generic metadata finalizers, owned IO-error diagnostics, zlib, bridge finalization, or outer response-outparam handling. [The closed version manifest](../../tests/node-compat/frameworks/nextjs/next-native-fetch-resource-cleanup-candidate-v2/version-manifest.json) identifies the corrected CPP and five inherited afterimages.

`EventLoop::cancel_async_task` roots/copies a task before removing it; `run_event_loop` roots a running task and drains ordinary jobs before its interest check. The interest check can exit before polling queued unreferenced work. These predicates are not a proof of host worker reuse, absent resources, or the cause of the fresh global epochs. Do not change interest policy or drop generic handles from this observation.

## Invariant needed before another implementation change

Design a separate, reviewed normal-input composition test through the existing guest `createServerHandler`, selected `node:zlib`/classic streams and unchanged WASI adapter. Use deterministic finite payloads, including output crossing the 64-KiB backpressure boundary, and an ordinary delayed reader. A Node reference should independently decode the complete gzip member and compare payload, CRC/ISIZE and EOF; compressed byte identity, chunk partition and timing are not required. No new server/host API, internal Store ID or native counter is needed. This is a proposed test, **not executed**.

The test's decisive invariant is: final codec output reaches bridge/Web-body readers before their normal EOF; the adapter observes that EOF before output-child retirement and exactly one successful outgoing-body finish; all normal completion promises settle without a retained stream error. Keep public raw bytes and settled event order before comparison. Specifically exercise a final output chunk that reaches readable backpressure, so `_flush` callback completion cannot conceal a lost trailer. Source-only ownership models can separately refuse finishing with a live output child or treating a typed finish error as success. Do not patch native append, bridge `_final`, compressor scheduling, or event-loop interest merely to make an unobserved branch fit the browser symptom. The existing public Fetch lifecycle and five-chunk passes remain narrower counterevidence, not this composed-path test or all-path cleanup proof.
