# Next.js bridge cancellation audit

This is a Source-only audit of the existing matched HTTP bridge, not a diagnosis of any captured redirect failure. No bridge, helper, Node, browser, guest, guard or target was executed for this audit. No behavior changed. The pristine standalone control's reported raw exit zero is **not** a same-app, same-workload comparison with the older bridge failures; it does not isolate a bridge defect or establish a fix.

## Shared bridge and completion boundaries

The [host bridge](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/bridge.mjs) and [HTTP foundation copy](../../tests/node-compat/foundation-http/next-http-candidate-v1/bridge.mjs) are byte-identical: SHA-256 `756580fcbb7940ea4fcd3135b9631b7c87c6a85b73d194b1adb251e9f28318f5`, 10,565 bytes. The foundation [generator](../../tests/node-compat/foundation-http/next-http-candidate-v1/generate-http-factory.mjs#L15) embeds that Source after import/export removal and explicit constructor guards. This describes the generation mechanism, not a new build or binary verification. The guest [createServerHandler](../../tests/node-compat/foundation-http/next-http-candidate-v1/http-core.mjs#L82) invokes `bridge.createRequestBridge(handler)` after readiness.

`BridgeServerResponse._write` ([lines 207–216](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/bridge.mjs#L207)) copies the submitted bytes before releasing the write callback and holds that callback while the Web stream queue is full. `_final` ([lines 218–220](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/bridge.mjs#L218)) already closes the Web body and calls back. `_destroy` ([lines 222–231](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/bridge.mjs#L222)) releases a pending write with an error and errors an unclosed body. There is no Source basis here for adding another unconditional close or finalization call.

These are independent completion boundaries: copying a producer's input protects that snapshot; the bridge's `finish` marks its Writable completion; the Node or WASI forwarding layer consumes the Web body; the host transport then has its own completion. None of the first three proves peer receipt or TCP completion.

## Concrete cancellation seam

The matched Node [forwarder](../../tests/node-compat/frameworks/nextjs/next-nonredirect-action-runtime-v2/run-stock.mjs#L152) converts the incoming Node message to a Web Request, copies the returned headers, and pumps the Web response. After `response.write(chunk)` returns false, [line 168](../../tests/node-compat/frameworks/nextjs/next-nonredirect-action-runtime-v2/run-stock.mjs#L168) awaits only `once(response, 'drain')`. Its response-close listener at line 156 aborts the input Request signal, but does not explicitly settle that drain wait or cancel the returned response body.

`BridgeIncomingMessage._read` [removes its abort listener after clean input EOF](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/bridge.mjs#L95). Output cancellation is a separate `ReadableStream.cancel` → `BridgeServerResponse.destroy` path at [line 136](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/bridge.mjs#L133). Consequently, a completed POST upload followed by a close-only host response while the output pump awaits drain or a body read has no explicit forwarding cancellation/settlement path in this Source. This is an uncovered control-flow seam, not evidence that it occurred in a retained failure.

The actual V2 app's `node_modules/next/dist/server/pipe-readable.js`, `createWriterFromResponse` lines 39–49, explicitly resolves its pending drain on response close. Its lines 103–111 separately await response `finish` after `end`. The native [WASI adapter](../../tests/node-compat/frameworks/nextjs/next-native-export-public-correlation-entry-v1/guest-entry.mjs#L705) instead observes output errors, cancels/releases the Web reader, drops owned children and finishes or drops the body; its conservative closed-output handling is at lines 729–758. These paths are contrasts, not interchangeable APIs or proof of universal cancellation safety.

## Tests before a behavior change

The existing [test-bridge.mjs](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/test-bridge.mjs#L39) checks a 128 KiB in-memory backpressured write, owned bytes and finish/close. Lines 55–61 abort an input that has **not** reached EOF. [test-wasi-adapter.mjs](../../tests/node-compat/frameworks/nextjs/http-bridge-candidate-v1/test-wasi-adapter.mjs#L162) checks output-error cancellation using explicit resource doubles; it does not run a component or the Node forwarding loop. None combines a completed upload, real host backpressure and a subsequent response close.

The smallest useful addition is a bounded Node transport test using the actual bridge and forwarding code: fully consume a POST, stream a fixed bounded response, pause the peer until a write is backpressured, then close it. Check that the forwarding task settles within its declared bound, cancellation reaches the Web response, pending producer writes settle, and original ownership cleanup completes. Keep a healthy full-drain/EOF case alongside it, plus a published-headers producer-error case. Do not turn a timeout into a semantic pass or add waits to the browser acceptance predicate.

A later real-Next regression should use the actual redirect action and unchanged strict worker. The current app's `node_modules/next/dist/server/app-render/action-handler.js`, `createRedirectRenderResult` lines 312–327, self-fetches the redirect target as GET, copies permitted response headers and returns `FlightRenderResult(response.body)`. That is the relevant streaming workload; an RSC-shaped test string is only a transport fixture. Ordinary response fields and separate `getSetCookie()` handling already exist in both forwarding paths, so this audit supplies no concrete header-copy change. Preserve every earlier failed gate and distinguish any future same-app/workload control from historical observations.
