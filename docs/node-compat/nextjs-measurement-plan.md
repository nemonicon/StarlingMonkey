# Empirical baseline for the working Next fixture

Design only, updated2026-11-07: no measurement workload, runner or result is created here. The current candidate is component `1c3108d2…` with engine `4623640b…` on stock Wasmtime42.0.1 against pinned Node22.14, using the fresh Next16.4.5/React19.3.1 app. The [fresh paired correctness records](../../tests/node-compat/frameworks/nextjs/next-app-runtime-root-results-v1/first-pair-review/README.md) remain separate evidence. The subsequent reliability cohort stays failed at5/6 despite native3/3; the new six-case request pair remains unexecuted. Measurements follow those application checks and the higher-priority rebuild work. This is not default-profile adoption or a claim that native code is faster.

The matched Node control is precisely the existing stock builtins plus [Module host provider and HTTP bridge](../../tests/node-compat/frameworks/nextjs/browser-hydration-matched-host-candidate-v4/run-stock.mjs). It listens before awaiting `app.prepare()`, then starts its own clients. Wasmtime's [fresh-app launcher](../../tests/node-compat/frameworks/nextjs/wasmtime-deployment-candidate-v7/deploy.mjs) reports a host listener before the guest's [lazy Next preparation](../../tests/node-compat/frameworks/nextjs/next-component-entry-fixes-v5/guest-entry.mjs). Their present listener/readiness intervals cannot be treated as equivalent application startup timings. The [direct standalone control](../../tests/node-compat/frameworks/nextjs/direct-standalone-control-root-results-v1/actual-review/README.md) supplies a separate unmodified-server comparison; its first24+2 correctness pass is not a timing or RSS measurement. Keep its expected server SIGINT130 distinct from the bridge and Wasmtime shutdown contracts.

Use a small instrumentation successor of these mechanisms, leaving app, component, bridge, providers and assertions unchanged. Move copying/authentication outside the timed interval and separate the matched Node server from the HTTP client/collector; otherwise its server PID's RSS also includes client/assertion work, unlike the Wasmtime server PID. Do not silently include the V8/V6 concurrent cold-request supplement in a31-request timing run; run its correctness gate separately and preserve its outcomes. The direct standalone controller already separates server and client processes, but still needs explicit timing/RSS collection before it can support a measurement.

Use one parent monotonic clock for these raw timestamps; preserve the raw events rather than subtracting a control:

| Observation | Definition |
| --- | --- |
| Launch | Immediately before spawning the server process, after setup/bookends. |
| Host listener | Node's actual listening event; Wasmtime's exact-address listener event. This does not establish Next readiness. |
| Node prepared | Existing `await app.prepare()` completes and the handler is installed; record separately. |
| First healthy application response | First `/api/health` attempt, status200 and complete valid fixture body. Start it after Node's prepared event, or immediately after Wasmtime's listener to trigger lazy preparation. Publish launch→complete-health as the primary startup observation, plus request start/headers/body-end. Preserve failures; no hidden health retries. |
| Follow-up response | Request start→headers and start→complete body on the same owned server process, with the declared reuse configuration. |
| Stream | Request start, first chunk, first shell marker, first ready marker and body end; retain exact chunks and require `readyChunk > shellChunk >= 0`. |

Stamp body end before hashing, asserting or writing results. Those checks still decide whether a sample is valid. A failed response is retained as failure, not converted into a latency sample for successful work. No guest clock or inferred internal `Next.prepare()` duration is needed.

The first finite run is **three paired trials**, sequentially ordered Node/Wasmtime, Wasmtime/Node, Node/Wasmtime. Each trial uses fresh server processes, independent byte-identical app copies and initially empty app caches; authenticate the actual2181-file/425-descendant-directory inventory and separate root record before/final. Preserve the native physical0444/0555 copy with its empty mountpoint/separate cache, and the stock source-mode copy that may gain ordinary `.next/cache` and `.next/server/route-cache` files. These are different filesystem policies, not equivalent descriptor rights or whole-copy immutability claims. Use fresh private host cache/config directories and record their initial/final inventories. Do not flush OS caches or mutate global caches; input hashing itself reads files. Call these *fresh-process/empty-app-cache* trials, not hardware-cold or isolated compilation measurements. Raw component loading/compilation remains part of the configured Wasmtime launch, with no precompiled artifact substitution.

After first health, issue one untimed warm-up round, then five measured sequential rounds of these five unchanged fixture cases: health, JSON POST, filesystem/SHA, public asset and streamed SSR. This is31 requests per process,186 total. Require the [existing body/status/JSON predicates](../../tests/node-compat/frameworks/nextjs/fixture-contract.json), complete bytes and strict stream ordering for every round. Wasmtime retains explicit reuse128/idle60; keep the total request count below128 and each gap below60s. “Follow-up under configured reuse” does not independently prove the same Store handled every request. Retain per-route first-visit observations, all five round samples and trial grouping. Report per-trial medians plus all raw values/ranges; the correlated requests are not15 independent process trials, and this small sample does not justify tail percentiles or a general throughput claim.

Run the unchanged24HTTP/cache/strict-stream/two-browser correctness gate after timing on the first pair. Keep browsers and concurrent builds/other target runs outside timing/RSS windows. Any failed trial stays failed; do not rerun until a favorable sample appears. Root checks available disk/memory before each fresh trial and issues finite original0af ownership/deadlines; any insufficient budget stops the planned series with partial results retained.

For memory, sample the exact live **server PID's public process RSS** with a separately owned observer, for example platform-verified `ps -p PID -o pid=,ppid=,rss=` every100ms. Retain PID/start identity, timestamps, tool/unit provenance, raw samples and missed samples. Report baseline/after-health/after-warm-up/after-round values and maximum *observed sampled RSS*. Exclude collector/browser/monitor PIDs from the server figure and report them separately if useful. RSS includes runtime, code/JIT, touched linear memory, libraries and allocator retention; it is not guest JS heap, native allocations, committed guest memory or a guaranteed peak. Host pool-reservation/default-heap policy logs are not RSS measurements. Do not subtract an empty host or assign a difference to an allocator without separate evidence.

Report raw component size **37,214,251 bytes** and SHA separately from the common fresh app **48,714,867 bytes**. The embedded engine is not an additional payload to add again. Record Node/Wasmtime executable identities and sizes separately; component-versus-executable sizes are not equivalent deployment-footprint measurements.
