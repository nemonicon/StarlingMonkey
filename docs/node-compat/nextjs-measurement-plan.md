# Empirical baseline for the working Next fixture

Design only: no measurement workload, runner or authority is created here. Measure experimental component `55f05e3d…` with engine `4623640b…` on stock Wasmtime42.0.1 against the pinned Node22.14 control, using the same Next16.4.5/React19.3.1 app. The [native first/repeat](../../tests/node-compat/frameworks/nextjs/next-intl-runtime-root-results-v1/hydration-v5-review/README.md) and [matched Node](../../tests/node-compat/frameworks/nextjs/next-intl-runtime-root-results-v1/hydration-stock-v1-review/README.md) correctness records remain separate evidence. This is not default-profile adoption or a claim that native code is faster.

The Node control is precisely the existing stock builtins plus [Module host provider and HTTP bridge](../../tests/node-compat/frameworks/nextjs/browser-hydration-matched-host-candidate-v1/run-stock.mjs). It is not an uninstrumented invocation of standalone `server.js`. It listens before awaiting `app.prepare()`, then starts its own clients. Wasmtime's [launcher](../../tests/node-compat/frameworks/nextjs/wasmtime-deployment-candidate-v5/deploy.mjs) reports a host listener before the guest's [lazy Next preparation](../../tests/node-compat/frameworks/nextjs/next-component-entry-fixes-v4/guest-entry.mjs). Their present listener/readiness intervals cannot be treated as equivalent application startup timings.

Root should first review a small instrumentation successor of these mechanisms, leaving app, component, bridge, providers and assertions unchanged. Move copying/authentication outside the timed interval and separate the Node server from the HTTP client/collector; otherwise its server PID's RSS also includes client/assertion work, unlike the Wasmtime server PID. No implementation is authorized by this document.

Use one parent monotonic clock for these raw timestamps; preserve the raw events rather than subtracting a control:

| Observation | Definition |
| --- | --- |
| Launch | Immediately before spawning the server process, after setup/bookends. |
| Host listener | Node's actual listening event; Wasmtime's exact-address listener event. This does not establish Next readiness. |
| Node prepared | Existing `await app.prepare()` completes and the handler is installed; record separately. |
| First healthy application response | First `/api/health` attempt, status200 and complete valid fixture body. Start it after Node's prepared event, or immediately after Wasmtime's listener to trigger lazy preparation. Publish launch→complete-health as the primary startup observation, plus request start/headers/body-end. Preserve failures; no hidden health retries. |
| Follow-up response | Request start→headers and start→complete body on the same owned server process, with the declared reuse configuration. |
| Stream | Request start, first chunk, first shell marker, first ready marker and body end; retain exact chunks and require `readyChunk > shellChunk >= 0`. |

Stamp body end before hashing, asserting or writing results. Those checks still decide whether a sample is valid. A failed response is retained as failure, not converted into a latency sample for successful work. No guest clock or inferred internal `Next.prepare()` duration is needed.

The first finite run is **three paired trials**, sequentially ordered Node/Wasmtime, Wasmtime/Node, Node/Wasmtime. Each trial uses fresh server processes, independent byte-identical app copies and initially empty app caches; authenticate the existing2218-file inventory before/final. Keep the same logical writable `.next/cache` and readonly app policy, documenting the different OS/WASI mechanisms. Use fresh private host cache/config directories and record their initial/final inventories. Do not flush OS caches or mutate global caches; input hashing itself reads files. Call these *fresh-process/empty-app-cache* trials, not hardware-cold or isolated compilation measurements. Raw component loading/compilation remains part of the configured Wasmtime launch, with no precompiled artifact substitution.

After first health, issue one untimed warm-up round, then five measured sequential rounds of these five unchanged fixture cases: health, JSON POST, filesystem/SHA, public asset and streamed SSR. This is31 requests per process,186 total. Require the [existing body/status/JSON predicates](../../tests/node-compat/frameworks/nextjs/fixture-contract.json), complete bytes and strict stream ordering for every round. Wasmtime retains explicit reuse128/idle60; keep the total request count below128 and each gap below60s. “Follow-up under configured reuse” does not independently prove the same Store handled every request. Retain per-route first-visit observations, all five round samples and trial grouping. Report per-trial medians plus all raw values/ranges; the correlated requests are not15 independent process trials, and this small sample does not justify tail percentiles or a general throughput claim.

Run the unchanged24HTTP/cache/strict-stream/two-browser correctness gate after timing on the first pair. Keep browsers and concurrent builds/other target runs outside timing/RSS windows. Any failed trial stays failed; do not rerun until a favorable sample appears. Root checks available disk/memory before each fresh trial and issues finite original0af ownership/deadlines; any insufficient budget stops the planned series with partial results retained.

For memory, sample the exact live **server PID's public process RSS** with a separately owned observer, for example platform-verified `ps -p PID -o pid=,ppid=,rss=` every100ms. Retain PID/start identity, timestamps, tool/unit provenance, raw samples and missed samples. Report baseline/after-health/after-warm-up/after-round values and maximum *observed sampled RSS*. Exclude collector/browser/monitor PIDs from the server figure and report them separately if useful. RSS includes runtime, code/JIT, touched linear memory, libraries and allocator retention; it is not guest JS heap, native allocations, committed guest memory or a guaranteed peak. Host pool-reservation/default-heap policy logs are not RSS measurements. Do not subtract an empty host or assign a difference to an allocator without separate evidence.

Report raw component size **37,214,436 bytes** and SHA separately from the common app **48,808,299 bytes**. The embedded engine is not an additional payload to add again. Record Node/Wasmtime executable identities and sizes separately; component-versus-executable sizes are not equivalent deployment-footprint measurements. No compression or build-time work is included in this run.

Keep clean-machine reproduction separate: source acquisition, toolchain/bootstrap, native build, component construction and their disk/time costs need their own pinned fresh-machine record. Existing successful artifacts and this proposed runtime baseline do not establish that reproduction, wasmCloud retained P2 support, production promotion, security or cost/performance advantage.
