This is an isolated **uncompiled Source proposal** for Next's real RNG demands. It leaves production, staged/frozen9aec, Byte09ac, timersc8f and all old crypto Source unchanged. It adds no key/provider/cipher implementation and performs no native build or target entropy operation. Every Source-peer/Root/build/component/guest/adoption slot is NULL.

In the retained406 compilation inputs, `next/dist/trace/shared.js:37` conditionally evaluates randomBytes(8).toString('hex') at load when neither trace ID exists. `next/dist/compiled/nanoid/index.cjs:1` refills a pool with randomFillSync. Atomic-file code uses randomUUID; bundled production encryption has conditional randomBytes(16/64) paths. Next also installs wrappers onto the mutable CommonJS crypto object and native webcrypto methods. Those source sites are static demand, not observed random draws. Dev-only preview keys, dev-server Uint32 draws and action-key generation are separately conditional; action manifests already carry a base64 key. No key bytes are retained here. Existing SHA256 digest('hex') support is preserved; base64 output digests/other Hash encodings remain deferred.

The new private C++ kernel uses exactly the audited native WebCrypto host primitive `host_api::Random::get_bytes` and the existing `web::crypto::random_uuid_v4`. It requires the real EngineInitialized state, unconditional shared deployed accessor and entropy::require **before** host entropy or allocation. It retains no native RNG handle or cache. Fixed U8 inputs/backing are rooted, the host call finishes before the JS byte pointer is reacquired, and copying occurs in a no-GC section. Returned host bytes are cleared on normal C++ returns using an owned scope guard. Traps/Storedeath and whole-memory erasure are not proved. UUIDs always use fresh entropy; disableEntropyCache is validated but no UUID cache exists.

The JS factory captures private kernel methods and the actual guest nextTick function at installation. randomBytes returns a genuine Buffer sharing the private fresh U8 backing. Nonzero callback calls draw synchronously then report via actual native FIFO (with its ALS registration capture); this is an explicit departure from Node's workerpool latency/resource identity. Zero callback calls are synchronous, matching actual Node22 source. Argument errors and the deployed guard are synchronous. Callback errors preserve falsy values and run through the real scheduler's error policy. randomFillSync supports fixed Buffer/U8/ArrayBuffer windows and returns its original argument. Other views, shared/resizable/detached buffers and >16MiB requests explicitly refuse. randomFill and randomInt remain coded unsupported APIs.

node:crypto.getRandomValues follows the current webcrypto.getRandomValues property, matching Node's delegation and allowing Next's actual dynamic-I/O wrapper to run. Secure bytes/randomFillSync/UUID instead use **captured private native backends**, so mutating public Node/WebCrypto methods cannot recursively redirect those secure backend calls. Native installer class checks for Crypto/SubtleCrypto remain unchanged. The CJS default becomes mutable only when the RNG argument is genuinely supplied, allowing Next to replace randomBytes/randomUUID; the ESM record remains frozen and its original named bindings do not automatically synchronize. No namespace-record alias fix is folded in. Hash/Hmac code is byte-preserved apart from factory arguments and the explicit CJS/default binding promotion; its existing INIT-live-EVP snapshot caveat remains open. This Source does not admit live Hash contexts at snapshot.

`after/cmake/builtins.cmake` is a genuine successor over held timer composition, with `NODE_COMPAT_CRYPTO_RANDOM` **default OFF**. Enabling it requires Hash profile, native WebCrypto, NEXT_STARTUP, actual internal ticks, and **RUNTIME_ONLY** entropy. The previous Hash entropy-OFF policy is loosened only for that explicit experimental configuration. This must generate a new classifier/recipe/cache/metadata and actual standard random import graph; the old83/OFF metadata cannot be projected. The public module manifest version is m0.23 with the exact existing full Node22 namespace inventory, not a selected subset. Its required standard random interface is a future policy; actual emitted version/type graph remains an integration gate.

`test-host.mjs` uses a clearly marked deterministic TEST ONLY provider plus real stock Node22 API-shape/randomness observations, actual host nextTick and ALS. No target provider/guest/key, crypto prototype, GC pressure, fault or reset workload runs. It checks INIT refusal before draw, sizes/fractional/errors, zero/nonzero callbacks, real offset views, fixed backing, cached backend behavior, CJS wrapper mutability, dynamic WebCrypto delegation and original namespace bindings. Those tests do not prove the native C++ kernel, entropy quality, ABI/link/snapshot/Store lifecycle or full guest Next behavior.

`generate-crypto-random-factory.mjs` runs in its actual future installed sibling layout, validates the public schema and includes both facade sources plus versioned manifest in the canonical digest. Normal CMake uses only the checked header; the main generator invokes this own generator only under its explicit `--crypto-random` Source-maintenance option. `integration.json` lists all changed/new installed paths and genuine parent descriptors. Packaging support copies are separate from installed new files. No whole SDK/history trees are duplicated.

Primary semantics are actual captured Node22 `internal/crypto/random` and crypto.js source and the pinned native WebCrypto/entropy/host APIs, all hashed in references. Frontend/link/review/newmetadata/full ordinary guest tests remain required. The host24+2 Buffer result is broad host evidence only: Root bridge and Node FS/crypto/zlib/streams can still produce host Buffer instances whose later prototype methods bypass that facade.
