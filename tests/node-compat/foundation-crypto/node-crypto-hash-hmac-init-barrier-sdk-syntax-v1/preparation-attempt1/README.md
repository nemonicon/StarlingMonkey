# INIT-barrier SDK syntax preparation

This is **UNSEALED, PREPARED, NOT EXECUTED**. It supplies one runnable driver for
two future SDK frontend checks of the held `b8a4f219…` three-file INIT barrier.
It is separate from that immutable Source family and from the native `9aec9297…`
engine/raw `2b725c11…` 83-field metadata. No new native variant, component,
snapshot behavior, Hash/Hmac execution or adoption is established here.

`plan.json` retains the actual entropy-policy.cpp and hash-hmac-kernel.cpp rows
from the Hash357 build's `compile_commands.json` (`2ebb84ea…`). Both rows already
select `NODE_COMPAT_CRYPTO_HASH_HMAC=1`, strict initialization, the Release flags,
the pinned SpiderMonkey includes and the guest OpenSSL include. The wrapper is
hashed and read, then replaced by its actual SDK30 clang++ alias/LLVM21 leaf
(`1aca933c…`); the wrapper itself is not executed. Borrow remains OFF. No new
macro, include-path guess or old355 compile row is substituted.

The two physical private main CPP copies and the changed entropy header will
be created only in the fresh external output after a compiler grant. A VFS
overlay maps **all three** original logical filenames to those private copies.
Each command removes the original `-c`, `-o` and writable dependency arguments,
retains the other actual flags and original compile-row working directory,
then adds exactly one `-fsyntax-only` and its own private `-MD/-MF/-MT` output.
There is no object, link, CMake, helper or engine command. The three separate
embedding source files are unchanged authenticated DATA, not a third frontend.

`run-sdk-syntax.py` uses the genuine original `0afae87d…` monitor (six positional
arguments; saved monitor `86913867…`) with a **60-second deadline per CPP** and
the original observed-process-group cleanup rules. Each unit retains the
monitor's actual `started.json`, stdout, stderr, owned observations and terminal,
plus a separate outcome and dependency provenance. A missing started record is
reported as missing evidence rather than an invented launch. A cleanup failure
stops the remaining command. A clean frontend diagnostic failure may still be
followed by the second syntax check; the combined result remains failed.

Before the custom monitor import or frontend launch, the driver authenticates
its own preparation family, all b8a4 Source members, the actual Source peer,
the monitor family, the original raw metadata/engine/DB/wrapper, pinned Python,
`/bin/ps`, and the literal donor source/dependency sample. It then hashes the
following exact current tree membership against the existing authenticated
`612818f6…` input ledger:

| Tree | Regular files | Symlinks |
| --- | ---: | ---: |
| SDK30 | 10,114 | 31 |
| SpiderMonkey include | 352 | 0 |
| Configured Source, excluding `.git` | 2,147 | 3 |
| Installed guest OpenSSL include | 135 | 0 |

Only descriptors and existing ledger references are kept here; no SDK tree is
copied. Every observed dependency must resolve to bytes authenticated **before**
the frontend, accounting for VFS mappings and the recorded SDK aliases. The
actual `.d` text is retained, including a partial file on diagnostics. Unknown
dependencies or a missing `.d` prevent success. SHA, size, mode, device, inode,
nlink, mtime/ctime, directory identities, aliases and canonical relative-name
sets are rechecked in the final/failure path. `.git` is explicitly outside this
syntax-input inventory. This does not pin the host OS loader/stdlib as a
hermetic operating system or prove C++ link/ODR/runtime behavior.

The alias donor's original before list used `sorted(Path)` while its final list
used `sorted(str)`. Those orders differ for names such as `foo/a.h` and
`foo.cpp` even with identical membership. This driver compares sets of relative
POSIX strings on both bookends. Synthetic missing/extra-member negatives and
the real ordering counterexample cover the correction. Its dependency parser
also reads the retained 1,041-name donor `.d` as DATA: all 1,040 non-main names
normalize to prior ledger entries. This is a parser/provenance check, not a
repeat compiler run or a prediction of the new units' dependency counts.

## Future Root authorization

The prepared `index.json` fingerprints this **unsealed preparation only**.
`root-authority-template.json` has no grant: source peer, compiler authority,
driver index and actual outcomes remain unissued/NULL. The driver rejects this
template. Root must independently accept the real b8a4 Source peer and issue a
separate authority naming that peer's indexed result, the final preparation
index, the exact two units/fresh output, syntax permission only, and all other
action flags false. This preparation does not create that authority.

Only after that separate grant may Root invoke the pinned Python with:

```text
/Applications/Xcode.app/Contents/Developer/Library/Frameworks/Python3.framework/Versions/3.9/bin/python3.9 \
  tests/node-compat/foundation-crypto/node-crypto-hash-hmac-init-barrier-sdk-syntax-v1/run-sdk-syntax.py \
  --execute-root-authorized-two-frontends '<JSON descriptor of the separately issued Root authority>'
```

The driver requires ordinary Python assertion execution (no `-O`), preserves
HOME/home/CODEX_HOME, uses a fresh controlled compiler environment/TMPDIR and
never implicitly retries an existing output. Final result and a complete output
index include all nested monitor evidence; only that index's own root filename
is excluded from its payload ledger. Physical filesystem/writer failure can
still prevent publication; no universal failed-write retention guarantee is
claimed. Source/SDK bookends on an actual run are still **pending**.

`test-driver.py` executes only extracted pure functions and synthetic cases; it
never imports the operational driver or monitor. `prepare-plan.py` only reads,
hashes and writes this unsealed plan/template. Do not rerun it after Root pins a
