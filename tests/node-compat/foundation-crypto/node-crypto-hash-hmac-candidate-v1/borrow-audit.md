# Proposed borrowing boundary, not runtime proof

The pinned SDK147 `js/experimental/TypedData.h` exposes `JS_GetObjectAsUint8Array`, `JS_GetTypedArrayByteLength`, `JS_GetArrayBufferViewBuffer` and `JS_GetUint8ArrayData`. The backing getter can materialize/allocate, so it runs before `JS::AutoCheckCannotGC`; rooted view/backing and state handle span the later pointer scope. The pointer is the view's byteOffset/byteLength window. Shared, resizable and detached backing is rejected before use; no getters, coercion, callbacks or JS allocations occur while borrowed. The repeated native length/shared check rejects a changed boundary. Zero-length updates skip the provider update.

OpenSSL 3.0.17 paths pinned by `source-inputs.json` are:

* `crypto/evp/digest.c::EVP_DigestUpdate` synchronously calls the selected digest update. `providers/implementations/digests/sha2_prov.c` registers `SHA256_Update`, through `digestcommon.h` wrappers.
* `crypto/sha/sha256.c` selects `HASH_UPDATE=SHA256_Update`; `include/crypto/md32_common.h::HASH_UPDATE` consumes full blocks synchronously and copies any remainder into the context. It retains neither the input pointer nor a JS object. The native SHA block implementation uses the supplied bytes within that call.
* `crypto/evp/mac_lib.c::EVP_MAC_update` dispatches the MAC update. Default `providers/implementations/macs/hmac_prov.c::hmac_update` with TLS parameters unset calls `HMAC_Update`; `crypto/hmac/hmac.c::HMAC_Update` calls `EVP_DigestUpdate` on its inner digest. This candidate never sets TLS HMAC parameters or supplies an ENGINE/custom digest.
* EVP_MD/EVP_MAC fetches explicitly request `provider=default`. The HMAC parameters also request SHA256 and default digest properties. Provider identity is checked at construction. This is a source-level restriction on this exact integrated OpenSSL, not acceptance of an arbitrary provider called `default`.
* `crypto/mem.c` supports customizable callbacks, so absence of a repository setter alone would not prove safety. The borrowing branch rejects unless `CRYPTO_get_mem_functions` returns the actual `CRYPTO_malloc`, `CRYPTO_realloc`, `CRYPTO_free` defaults before update. Those defaults use C allocation and do not call SpiderMonkey. Error queue allocation, if any, is native; errors are converted to JS only after leaving NoGC. No OpenSSL RNG API is called in the candidate. Provider initialization/configuration occurs before borrowing and can have broader native effects; a future actual zero-import/entropy-OFF artifact and initialization audit is still required.
* The accepted repo WebCrypto uses owned BufferSource copies around JS normalization/Promise work; that asynchronous path is not directly reused. The Buffer kernel's allocation-before-borrow and rooted NoGC pattern supplies the JSAPI precedent.

The default copying baseline permits measuring the cost of a conservative owned input independently. No benchmark was run. Enabling borrowing requires an independently reviewed integration, actual SDK frontend success, full default-provider/config/link provenance, moving-GC/lifetime/error tests in an explicitly authorized future phase, and actual import/snapshot checks. It cannot establish correctness for shared/RAB storage, user callbacks, provider replacement, a multi-threaded JS mutation race, or arbitrary OpenSSL allocators.
