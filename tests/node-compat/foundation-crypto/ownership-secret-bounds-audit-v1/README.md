1. **P1 — allocation before null check:** crypto-algorithm.cpp30–43 writes through the JS_malloc result in to_bytes_expand; callers check the pointer afterward. A failed nonempty allocation can therefore reach fill/BN_bn2bin first. No allocation failure was induced.
2. **P2 — partial BIGNUM output ownership:** five EC/RSA extraction groups,15 get_bn_param calls, construct owners after short-circuit checks. Earlier successful allocations escape when a later extraction fails; the optional RSA CRT fallback returns before adopting its partial outputs. OpenSSL p_lib.c2154 and params.c921 allocate/write caller-owned BIGNUM outputs.
3. **P2 — EC point buffer leak:** crypto-key.cpp491–505 obtains an OpenSSL-allocated point buffer and never frees it, including on successful import. ec_oct.c137–157 confirms that success transfers the allocation. The buffer must remain alive through OSSL_PARAM_BLD_to_param; freeing immediately after push would be wrong.
4. **P2 — checked lengths and allocation behavior:** HMAC data->size()*8 is unchecked on wasm32; size_t is passed to EVP_PKEY_new_mac_key(int), make_bignum narrows to int and DER decoders accept long. Bounds/reachability and error parity need a separate finite cut. The observed -fno-exceptions build does not gain recoverable std::vector/new OOM from if(!data).
5. **P2 hardening — secret copies:** existing wiping covers logical owned HMAC vector/raw BufferSource copies. It does not cover decoded JWK std::string, EC/RSA private component strings, private serialization buffers, ordinary BignumPtr(BN_free), or ordinary OpenSSL param storage. No all-copies erasure/finalizer/free/wipe claim follows.
