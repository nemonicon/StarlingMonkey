This packet verifies a possible linker concurrency control. It contains no native build, guest execution, memory measurement, recipe modification, or filesystem representation change. A lower build RSS or temporary-disk peak remains unverified. The existing 2 GiB launch gate and 800 MiB stop threshold remain in force.

The installed WASI-SDK reports 30.0 and LLVM/LLD 21.1.4 at LLVM commit `222fc11f2b8f25f6a0f4976272ef1bb7bf49521d`. Its actual help supports `--threads=1` and `--thinlto-jobs=1`. In the pinned [`readConfigs`](https://github.com/llvm/llvm-project/blob/222fc11f2b8f25f6a0f4976272ef1bb7bf49521d/lld/wasm/Driver.cpp#L625), the first option configures LLVM's parallel strategy and supplies the default ThinLTO job count; an explicit ThinLTO option can override that count. The pinned [`BitcodeCompiler` constructor](https://github.com/llvm/llvm-project/blob/222fc11f2b8f25f6a0f4976272ef1bb7bf49521d/lld/wasm/LTO.cpp#L70) uses this count for its in-process ThinLTO backend. These are supported controls rather than inferred environment variables.

The current completed ordinary Release project's final Ninja command has `-O3 -DNDEBUG -flto=thin` and no LLD thread limit. The launcher explicitly sets Ninja, Binaryen, Rayon, and Cargo concurrency to one. The actual Clang wrapper forwards its arguments to SDK Clang, and Clang's printed linker command still has no `--threads` or `--thinlto-jobs` option. Those other tools' controls therefore do not establish an LLD concurrency limit for this invocation. The launcher `launch.json` prelaunch state field is preserved as such; this audit does not use it as terminal-build evidence.

`capture.py` ran only `ninja -t commands`, tool help/version commands, and Clang's `-###` print-only mode. The latter was run for the original command and a proposed command with `-Wl,--threads=1,--thinlto-jobs=1`. The printed LLD argument arrays differ by exactly those two arguments. Neither printed job was executed. The explicit ThinLTO argument is redundant when the thread count is one and no override is present; retaining both in a future recipe would make the intended limits explicit. The actual post-link `wasm-opt --strip-debug -O3` command is recorded separately and has not been changed or executed by this audit.

The proposed experiment is in `future-measurement-plan.json`. A future producer would add the two linker options through the existing `CMAKE_EXE_LINKER_FLAGS` configure setting, whose current directory-scope use is in `cmake/compile-flags.cmake`. It needs a new reviewed recipe, policy, artifact namespace and receipt. Current recipe `1e2f15d1...` must retain its existing meaning. The experiment must record both the cache input and the actual driver-expanded LLD arguments; a cache entry alone is insufficient. Existing native 306 plus diagnostic two source inputs, strict/layout flags, optimization settings, Rust lock, OpenSSL, SDK, embedding patches, and the full ordinary/GC validation scope must remain explicit.

First compare link-stage resource use from identical input bytes, then validate any new full artifact normally. Serial trials must preserve the inputs, existing artifacts and all their receipts. Use short distinct namespace replacements instead of extending already long basenames. Measure elapsed time, process peak RSS, sampled process-group RSS, minimum free filesystem space, and created/allocated output bytes separately. A smaller RSS would not establish a smaller disk requirement, and neither establishes that a sub-2-GiB launch is safe. No benefit is assumed, and no operational threshold is waived.

Changing LTO optimization levels, codegen partitions, caches, saved intermediates, SDK sources, C++ inputs, diagnostic flags, test scope, or host behavior is outside this proposal. The stopped fault/debug and SDK-compaction branches remain stopped. Cross-build binary identity is to be measured rather than assumed; successful ordinary functional, import/export, unsupported-operation, initializer, ABI, scheduler and Release-GC gates are still required for a new artifact.
