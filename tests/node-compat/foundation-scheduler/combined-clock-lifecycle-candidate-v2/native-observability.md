# Missing native evidence and the minimal diagnostic proposal

The actual combined355 `Engine`/`EventLoop` APIs provide queueing, cancellation, interest increment/decrement, `has_pending_async_tasks()` and the optional `AsyncTask::select` result. They provide no read-only queue length, interest count, timer-registry size, pending Promise-job count, subscription/drop count or cached immediate-pollable ownership record. Timer retirement drops/invalidate-first and clears traced edges in Source; observing zero callbacks is not a measurement of those actions. `has_pending_async_tasks()` alone is not full quiescence.

The historical `BoundaryTask` diagnostic extension demonstrates real `add_builtin(diagnostics::internal_ticks DISABLED_BY_DEFAULT SRC ...)`, `Engine::define_builtin_module`, TaskQueue tracing, task-owned interest and idempotent completion. Its `diagnostic_pending_tasks` counts only that fixture's own tasks. It observes neither current TimerTask nor total interest/pollable state, and its old306/308 or later342 receipts must never be admitted as current355 evidence.

Proposed separate diagnostic generation (no C++ implementation is included here):

* Add a disabled private builtin, e.g. `diagnostics::clock_lifecycle`, through the existing `CMAKE_PROJECT_ComponentizeJS_INCLUDE` and `add_builtin` mechanism. Expose a captured native record with `Engine::define_builtin_module("starling:test-clock-lifecycle", ...)`, without a production Node/global export or host service. Thread an explicit `NODE_COMPAT_LIFECYCLE_DIAGNOSTICS` macro through the genuinely new target/source policy. Only the actual new CMake/native manifest may determine its counts; adding a TU/header/CMake fragment and modifying instrumented sources is not an unchanged355 inventory. Preserve the355 parent as an explicit partition and require a fresh full ABI/dependent rebuild.
* Instrument real TimerTask registration/retirement/destruction, actual MonotonicClock subscribe/drop-return sites, selector prune/poll branches, EventLoop task/interest transitions and the genuine embedding call/post_call boundaries. Retain fixed-size primitive diagnostic records; reject overflow and never truncate to claim success. Counters must not add strong JS roots, allocate during GC or alter production ordering. Read-only accessors alone are insufficient without native event histories at those transitions.
* Record each acquisition with an internal monotonically increasing lease serial distinct from a potentially recycled numeric WASI handle. For each real timer lease retain acquire-return, invalidation-before-drop, drop-attempt and drop-return counts, plus current owned lease count and registry/task state. A returned drop proves the standard drop call returned; it does not independently inspect the host resource table. Do not read memory, forge an integer handle or force a host trap. Require at most one returned drop per acquired lease, no drops of unacquired leases, and no timer-owned live lease after the case's fence/terminal boundary.
* Observe total interest at a true boundary **after** the embedding's fulfilled/rejected reaction has released its own outer-call interest. A getter executed inside a fresh export necessarily sees that export's own interest; it cannot truthfully require total zero there. Preserve a previous-boundary POD snapshot, tagged with the completed call sequence, and expose it on a later diagnostic read. Similarly record post_call's `cur_fn_idx` and free-list boundary only after actual post_call. Do not overwrite/zero interest, clear error tracking, or call reset in order to pass.
* Read-only observations of finalizer/tick/Promise queues require actual existing queue APIs or new explicitly reviewed accessors. `js::RunJobs` completion does not prove no future native completion can enqueue; do not claim owner/request quiescence from one count. Failure/unknown ownership poisons the instance for disposal; no reuse permission follows.

Required native test seams:

1. **All invalid, interest released by pruning.** Queue a bounded private AsyncTask subclass using actual protected `handle_ = INVALID_POLLABLE_HANDLE`. Its explicitly owned interest keeps the loop alive after the already-fulfilled outer export reaction releases the outer call's interest. The last fixture task owner/destructor releases only that fixture's interest when the selector erases the invalid row, with no JS call/allocation. Require no extra surviving RefPtr owner at that point. Then nullopt/continue must revisit the now-zero interest boundary and complete. Releasing all interest before selection would exit at the earlier interest check and would **not** test pruning. Check actual pre/post interest, pruned count, nullopt and zero empty-poll attempts. JS clearTimeout removes queue entries and cannot reach this selector branch. Do not invoke run_event_loop recursively inside a guest callback. This is a proposed fixture-owned lease contract that needs its own C++ lifetime review; it is not a claim about TimerTask interest ownership.
2. **Invalid plus survivor.** Mix invalid fixture tasks with immediate tasks preserving enqueue order. A real task/Promise owns outstanding interest until the survivor runs. Check no early successful exit, each survivor callback once, expected order, no invalid indexing and exactly-once fixture interest release. An all-invalid queue with deliberately outstanding owned interest must terminate through the existing no-task failure in a fresh disposable child; never hang or label it success.
3. **Real timer leases.** Run all seven unchanged cases and the survivor fixture under the newly compiled diagnostic variant. Check per-lease histories, timer registry/task counts and callback root lifetime. These supplement the raw scalar observations; private dummy tasks do not prove timer drops or real pollable semantics.
4. **Immediate cache.** The actual static `immediately_ready` owns one subscribe-duration(0) pollable once the mixed immediate/real branch is reached. No explicit drop/reset path is present in current Source. First observe its initialization, stable reuse and ownership separately from timer leases. Process exit/group cleanup does not prove an explicit native drop or same-instance teardown. Do not silently assert all native resources are zero while the cache survives. An explicit bounded disposal/drop design is required if that is the acceptance requirement.
5. **Snapshot clock offset.** Existing `runtime/js.cpp` saves `mono_clock_offset` during wizen and adds it only for CLOCK_MONOTONIC; CLOCK_REALTIME bypasses it. A private read-only fixture can report exact integer pre-snapshot raw monotonic, saved offset, resumed raw monotonic and adjusted result, retaining u64s as decimal strings. Check `adjusted = raw + offset` in the actual nonoverflow domain. This requires new native observation/registration Source and actual construction/resumption; a JS performance sequence alone cannot show the underlying offset, and unrelated hosts' clock epochs must not be compared.
6. **Disposal.** With no pending work, record last event-loop and post_call state, then stop the owned host child and retain terminal/group cleanup. This establishes bounded process disposal only. Native destructor execution/explicit WASI drops require records from those actual paths. Full same-instance teardown/reset, HTTP/stream cancellation, closing-registration refusal, request epochs and ALS remain unsupported rather than tested by the unsafe old reset.

All new diagnostic engine/metadata/receipt/source policies, packaging graphs, guest roots and actual results must be separately authenticated. Its instrumentation and extra imports must be explicitly counted; original production metadata80 and engine355550 remain unchanged. Standard selected WASI interfaces remain the boundary, with no custom test host and no DEBUG/OOM/GC-pressure operation.
