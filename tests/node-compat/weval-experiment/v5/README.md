# Frozen v5 Weval experiment

This version uses the exact validated production v5 OFF + Path + Events engine/source freeze. The original parent-directory recipe/pins remain historical v3 templates; they have not been rewritten to describe a later baseline. This experiment changes no production source, repository build recipe or host runtime.

[pins.json](pins.json) binds engine SHA `165b59a1fac4f3bab14547a28063908193c2b98767bd5fa835ca00b9b6d8adfc`, its exact sidecar, all 271 source paths/digests, the frozen recipe `ef3c91e7b9c20745600a040645e83c41013a44a16184e9ab2f12edda010f84ab`, frozen complete OpenSSL auditor and the three native embedding files. The ordinary production encoder is SHA `32230064c1ea0bc66ffbc5f9ddd6a97f46a8bc47a7c9e72caaddf5745f8986c7`. Earlier private codec/fault helpers are outside this source set.

[build-engine.mjs](build-engine.mjs) verifies those inputs, clones a separate external source project and overlays only the accepted native source freeze. Its private [recipe transformation](recipe-transform.mjs) changes the release archive/distribution to `release_weval`, selects `WEVAL=ON` / `USE_WASM_OPT=OFF`, selects hash-checked Weval and Binaryen executables, and uses a separate `_weval` output/artifact name. The unmodified frozen CMake implements this pipeline. Path and Events are explicitly ON, with Release, locked Rust, strict initialization, entropy OFF, WPT/debugger/GC-stress/OOM instrumentation OFF. Native and ComponentizeJS embedding source manifests must exactly match the validated base after build. The transformed script passes `bash -n`, and its inspected diff is retained outside the checkout.

The three downloaded official release archives were extracted, and their actual Weval/wasm-opt/libbinaryen payloads match the audited hashes. Weval is [0.5.1](https://github.com/bytecodealliance/weval/releases/tag/v0.5.1), Binaryen is 123, and SpiderMonkey uses the [147 release_weval asset](https://github.com/bytecodealliance/StarlingMonkey/releases/tag/libspidermonkey_FIREFOX_147_0_4_RELEASE_STARLING). SDK30 and the existing pinned cbindgen/CPM cache are shared; source/build/artifact namespaces are separate. This is a cache-assisted reproduction, not a clean-machine build claim.

The first build uses four Ninja/Make jobs, `RAYON_NUM_THREADS=4` and `RUST_MIN_STACK=67108864`. Application packaging must also select `aotMinStackSizeBytes:67108864`, the explicit verified Weval binary and **this engine's own** `aotCache`. The existing CMake target generates a generic IC cache from `null.js`; it is not application training. The driver verifies its actual command, binds the cache to the byte-identical raw embedding, and copies it to a separate artifact before any rebuild. It records actual cache/tool/configuration hashes and verifies its own driver sources before/after execution.

```sh
NODE_COMPAT_WEVAL_BASE_ENGINE=/tmp/starling-node-compat/foundations-v5/native-freeze/off-path-events.engine.wasm \
NODE_COMPAT_WEVAL_SOURCE_FREEZE=/tmp/starling-node-compat/foundations-v5/native-freeze/source \
NODE_COMPAT_WEVAL_BASE_RECIPE=/tmp/starling-node-compat/foundations-v5/native-freeze/build-engine.sh \
NODE_COMPAT_WEVAL_BASE_AUDIT=/tmp/starling-node-compat/foundations-v5/native-freeze/openssl-source-audit.py \
NODE_COMPAT_WEVAL_BUILD_ROOT=/tmp/starling-node-compat/weval-experiment/custom-release-v5-1 \
/tmp/starling-node-compat/node-v22.14.0-darwin-arm64/bin/node tests/node-compat/weval-experiment/v5/build-engine.mjs --build
```

Only a new namespace is admitted. A failed build is preserved and is not silently resumed by this driver. Logs and receipts live under `/tmp/starling-node-compat/weval-experiment`. General DEBUG indirect bindings and all stopped fault work remain excluded. Native-versus-Jco arms must share the identical selected engine/cache/tools/options; ordinary-versus-Weval comparisons must disclose the different static-library and wasm-opt pipelines, rather than claiming a single isolated switch.

## Completed build and ordinary component gates

[build-receipt.json](build-receipt.json) and the byte-identical [native metadata](engine.build.json) record engine SHA `22b771cd36d5834f56059f831ecfbf8636ab925270973f35079b4bd5f7f72a4e` (10,987,910 bytes) and matching generic cache SHA `f6fe62009691fe5ffc8535e58abd648d3006f4727b003f219b866de0270042ff` (5,029,888 bytes). All 271 native and three embedding inputs exactly match the production v5 base. Actual observed flags, `--locked` Cargo commands, all 4,650 OpenSSL source files, tools, release configuration and raw-engine/cache command binding passed. Read-only peer review found no substantive build/guard issue.

[run-smoke.mjs](run-smoke.mjs) passes **58 checks** in the [actual smoke component](smoke-results.json), including three retained Jco calls and fresh Wasmtime 42 calls. Its 12 valid WIT exports exercise full-boundary u32, negative s32, f32/f64 including special values, high u64, negative s64, string/list/record/result values, Node Buffer checksums, snapshot backing identity, Path/Events behavior and first deployed dynamic `node:child_process` import. The component has **zero imports**. Top-level unsupported call/construction and an unhandled initializer rejection all correctly fail componentization. This is bounded smoke coverage, not the earlier complete ABI/codec/Buffer corpus.

This Weval version has not rerun the complete guest-to-guest callback ABI, Unicode/codec and Buffer corpora, rooted-GC variant, RuntimeOnly entropy policy or selected HTTP deployment on wasmCloud. Ordinary-v5 results for those gates remain separate. The smoke's real public WIT argument/return checks support its bounded claims; static-library configuration alone does not prove those additional paths.

An initial test asserted that Rolldown's static-import list included its separately preserved dynamic import; it failed before packaging. A later test expected the unsupported error's `.code` in printed stderr, but stderr prints its human-readable `.message`. The [ordinary initialization diagnostic](initialization-results.json) proves the actual rejection was already correct. The corrected smoke validates the identifiable `.code` inside a caught deployed call and the specific module/operation message during initialization. Exact failed logs/runner are preserved in the [functional receipt](functional-artifact-receipt.json); no native or policy workaround was applied.

[package-arms.mjs](package-arms.mjs) builds native and **actual Jco 1.40 / unenv 2.0.0-rc.24** Buffer arms against the exact same engine, generic cache, verified tool, v2 splicer, library and explicit feature-OFF options. Their supported workload source is the unchanged corrected-clock benchmark. Both match Node setup/full and operation checksums in all **20 scenarios**; snapshot checks prove implementation/global-Buffer identity and prevent native contamination of the JavaScript arm. Both emit zero imports. [App artifacts](app-artifacts.json) record native `8ef3f325…` (17,761,277 bytes / 5,302,460 gzip) and Jco `586d96cc…` (19,223,955 / 5,669,134). These are single componentization size observations, not replicated minimum sizes.

The recorded one-off componentization times (native about 7.02 seconds, Jco about 5.10 seconds) include initialization/specialization and run in fixed native-then-Jco order. They are provenance, not controlled packaging-speed evidence; tool/OS warmup and scheduling can differ. The generic cache is read-only and unchanged, while each application's specialization is distinct.

The benchmark compares the shared supported operation subset. Native and Jco adapter API coverage differs; matching these checksums does not imply equivalent complete Buffer surfaces. The additional JavaScript/global adapter can retain code for methods outside the measured subset, so its component-size increment is a deployment observation for this selected configuration, not the cost of an identical complete API implemented in two languages.

The unchanged Wasmtime 42 benchmark host (`f7fb77…`) separately [compiled both components](compilation-results.json). [measure.mjs](measure.mjs) keeps compilation out of throughput timing, requires all artifact/source/cache hashes to match, and retains per-instance startup, setup, first-batch, warmed timing, RSS and desired linear-memory data. Its two rounds reverse each scenario's arm order, using seven batches and three fresh instances per arm/scenario/round. The [completed measurements](RESULTS.md) cover 80 arm/scenario runs, 240 fresh instances and 1,680 timed batches. Native hex/UTF-8 codecs are faster here, but the small `Buffer.from(existing Buffer)` constructor and several memory cases are counterexamples to a uniform win. The separately built Weval `libcrypto` archive differs from ordinary v5; no one-variable ordinary/Weval causal comparison follows from this native/Jco pair.
