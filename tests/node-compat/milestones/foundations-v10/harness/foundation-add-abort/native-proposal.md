# Protected abort listener proposal — uncompiled

This is a dependency-ordered engineering proposal based on the files in [source-audit.json](source-audit.json). None of the identifiers introduced below is an existing embedding API. There are no production edits or compiled templates in this folder.

## 1. Preserve the public facade contract

Use a small audited JavaScript facade for validation order, structural object acceptance, actual dynamic `signal.addEventListener`/`signal.removeEventListener` lookup, null-prototype result, and the target's captured `Symbol.dispose`. The ordinary declaration already supplies a real ESM export and default-object relationship; update its versioned manifest only when selected tests pass.

Do not implement the public method by registering `AbortAlgorithm::run`. Apart from missing removal, an algorithm is not an Event listener: it precedes event creation, never sees synthetic dispatch, and cannot preserve deduplication with an existing ordinary listener. A universal wrapper callback would also change duplicate identity and public `removeEventListener` behavior.

An internal protected-options symbol is one possible bridge. Create and root it once during selected profile installation; pass it through the events factory's finite private argument, not a new global or host import. Extend existing option flattening to recognize precisely this key and set a listener flag. The facade then calls the public signal method with `{__proto__: null, once: true, [key]: true}` and the original callback, preserving overrides and fake signal behavior. The key is an implementation detail, not a security boundary: a structural receiver may observe its options. Do not silently mark every ordinary abort listener protected.

The current events factory receives `undefined`. Selecting a native helper would therefore require an explicit, bounded factory-kernel contract and optional CMake dependency on the existing web EventTarget/AbortSignal targets. Determine those targets from the actual `add_builtin` setup before editing it. Keep optional events OFF applications free of the new registration state and imports. No cryptography, filesystem, clock or random dependency follows from this operation.

## 2. Reuse target-owned records and make removal precise

Retain the existing `EventTarget::ListenerList = JS::GCVector<RefPtr<EventListener>, ...>` and its `GCPolicy<RefPtr<T>>`. Add finite record flags for protected Node event dispatch if chosen; do not store raw moving-GC pointers or a process-global map of callbacks. All new JS edges, including an optional execution cell or owner reference, must be `JS::Heap` fields traced by the record and every temporary list clone.

Use the original `(callback, type, capture)` equality. On an existing tuple, preserve all original flags and do not allocate a second listener. Mark a once record removed **before** invoking user code so nested dispatch cannot repeat it. Disposal/removal during dispatch marks the shared record, then erases the target's ownership; the rooted cloned list keeps it alive until the frame completes. A removed future record is skipped. Compaction and event flag/currentTarget cleanup must run on normal completion, propagation stops and exception paths; a cleanup guard can avoid the current early-return omission.

Protected dispatch must continue scanning the original listener order after propagation stopping, skipping only unprotected records. The callback receives the actual event target as `this` and one original Event. Synthetic events have `isTrusted=false` and must consume the once record without changing signal.aborted. Controller abortion sets reason first, creates a trusted Event, and dispatches it through this same path. Do not separately invoke the callback in the abort algorithm list.

Retaining the exact JavaScript disposer closure naturally keeps its signal/callback reachable while the disposable remains reachable, even after disposal. Repeated dispose performs another dynamic remover lookup, as the Node oracle shows. Do not claim immediate callback collection merely because the target list entry was removed. A native registration handle, if later added for internal consumers, needs a distinct documented idempotent contract; it must not silently replace these observable facade side effects.

### Existing `{signal}` cleanup dependency

`EventTarget::Terminator` is stored in a different signal's unique-owned algorithm list and strongly traces the target/callback/options. The target record currently has no backlink/token to unlink it on ordinary removal or once completion. Introduce a **proposed** stable removable abort-algorithm registration, rather than retaining a vector index or `AbortAlgorithm*` across mutation. A refcounted state can have an active flag plus traced callback edges and an owner-list reference; removal marks it inactive and clears ownership, while an in-progress rooted/refcounted snapshot keeps it alive. IDs must not be reused within the owner's lifetime, and overflow must fail predictably rather than alias a previous registration.

This general hook needs its own API/error review. `add_algorithm` currently conflates already-aborted and allocation failure and has no `JSContext*` parameter for reporting OOM. A replacement must distinguish "already aborted/no registration" from an allocation error, report failed native allocations through existing guest exception APIs, and roll back partial target/algorithm insertion. Destruction must delete the allocated algorithm/weak-set containers exactly once. Existing `AbortSignal::finalize` currently deletes neither those containers nor their contents; it calls only `EventTarget::finalize`. Do not erase a unique-owned vector element while its `run` method is on the stack.

These are proposed internal guest APIs, not standard host services or SpiderMonkey extensions. The public addAbortListener path itself needs no auxiliary abort algorithm because it is a protected EventTarget listener.

## 3. Decide error and microtask semantics explicitly

Source Node dispatch queues thrown listener errors for uncaught-exception reporting and observes Promise-like callback results. Starling EventTarget currently prints/clears pending exceptions and ignores the returned value. Its queueMicrotask creates a Promise reaction, so a throwing callback becomes a rejected reaction. Neither route establishes equivalent behavior.

Add a finite guest error-report queue using traced values/stacks only if a versioned profile policy is selected. Dispatch should continue remaining protected listeners, restore context/event state, and enqueue the original thrown value without calling arbitrary user getters while holding unrooted values. Queue draining must have an explicit ordering relative to Promise jobs and other tasks, and a terminal entry-boundary behavior for errors when no supported guest error handler exists. A process API is not available by implication. If the first bounded implementation chooses an identifiable entry failure instead of Node's process/nextTick reporting, declare it partial and test the deviation; do not label it fully supported.

The [ordinary Release diagnostic](initialization-results.json) confirms this is already a snapshot-policy defect: two synchronous listener exceptions from unsupported top-level `spawn()` calls are swallowed, whereas direct/async-listener/microtask controls fail. The current strict checkpoint only checks `unhandledRejectedPromises`; a synchronously cleared exception never enters that set.

A narrow **proposed** strict-profile remedy is an engine-owned traced record of unreported event exceptions, with a final initialization checkpoint alongside the existing rejection check. Record the original exception before clearing it for continued dispatch. A caught exception inside the listener creates no record. After jobs/finalizer jobs drain, any unreported record rejects componentization; it must not disappear when stderr is disabled or reset clears Promise tracking. This can close the snapshot requirement without pretending to implement Node process/nextTick reporting. A bounded record policy must specify how multiple errors and allocation failure are handled.

For deployed execution, an internal `api::AsyncTask` subclass is a possible terminal-report vehicle: set `handle_ = IMMEDIATE_TASK_HANDLE`, retain traced exception/stack/resource edges, increment event-loop interest when queued, and decrement exactly once on run/cancel. `EventLoop::run_event_loop` drains Promise jobs first and otherwise stops immediately when interest is zero; queuing a task without interest is insufficient. The current selector can call standard poll/monotonic-clock functions when an immediate task follows real pollable tasks. Therefore a dedicated guest-only report checkpoint before host selection may be preferable for capability-free applications; verify emitted imports rather than assuming that every "immediate" path avoids host functions. This is a proposed queue change, not an existing `queue_uncaught_error` embedding API. Error teardown must report before request reset, and cancellation must not silently erase an outstanding fatal report. No host modification/service is required.

For the already-aborted path, queue a callable which invokes the original listener with undefined `this` and no arguments. Disposal must not cancel this queued operation. Use an audited native job/error path or demonstrate that the facade's queue semantics meet the selected policy; do not rely on an unhandled rejection as an undocumented substitute. Promise-like return handling applies to event dispatch; the exact already-aborted microtask return behavior requires a separate test and contract. The current Node oracle covers synchronous listener throws, not async-return reporting.

## 4. Keep execution context and request ownership separate

Do not capture and restore an ALS cell for every event listener by default. A synchronous event callback runs within the dispatching resource, and changing its ALS context to registration time would be observable. The queued already-aborted callback must capture the registering resource's execution state at actual job registration. The Node oracle records both; the [ALS architecture](../async-context/architecture.md) identifies SpiderMonkey 147's real `getHostDefinedData` hook and the remaining Promise/private-record limits.

Any later internal stream cancellation adapter must distinguish the caller's current execution cell, a stream's explicitly created AsyncResource, and the request that owns live handles. A request-owned registration is removed when its owner is cancelled/closed; cleanup runs under the owner's chosen resource cell before releasing guest resources. An application may deliberately retain a signal or AsyncResource across component entries, so do not blanket-clear every application listener after a request or disable ALS instances to simulate owner expiry.

Snapshot initialization may create ordinary guest signals and inactive/live listener records, but it must not capture deployed request handles or environment identities. Pending already-aborted jobs should be drained by the existing initializer checkpoint; callback exceptions must obey the same strict initialization boundary policy as other application top-level errors. At deployed entry, begin with a fresh execution cell and an explicit owner; do not infer a universal deployment boundary solely from `EngineState::Initialized` or the shared FetchEvent singleton. Repeated component calls must not inherit the last request's current cell, pending report queue or live handles.

## 5. Required gates before selection

1. Run the checked-in Node oracle unchanged as the reference, including duplicate/ordinary pre-registration, disposer reentrancy, synthetic events, structural fakes/getters, stop protection and exception ordering. Keep exact Node22 symbols and target's documented symbol identity deviation separate.
2. Reuse the existing component harness with only valid public APIs. Run a snapshotted initializer case, two retained Jco calls and fresh stock Wasmtime; verify exact exports and zero final imports. Add no host callback service.
3. Test removal before dispatch, during an earlier listener, from itself, after once completion, duplicate disposers, nested synthetic dispatch and registration inside a real abort callback. Verify callback counts and event target/currentTarget cleanup. Allocation ownership and GC safety require a separately authorized appropriate gate; ordinary callback counts alone do not prove collection.
4. Select and validate listener throw/rejected-result reporting before marking the method supported. No uncaught error may disappear solely because a stderr interface was stubbed.
5. Add actual registration-time job and entry/owner cleanup hooks only with the corresponding ALS/request resource gate. Current isolated ALS prototypes are not installed production support.

Until these gates pass, keep `addAbortListener` explicitly deferred; classic stream abort/pipeline support remains blocked on this dependency or must declare a narrower, separately tested cancellation contract.
