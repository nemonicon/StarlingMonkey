This is an **unsealed, uncompiled implementation draft**, not an installed `node:async_hooks` module or a propagation result. Live production C++ is unchanged. No engine, fixture, key, compiler, GC-pressure, OOM, reset or guest operation has run. Root/action/review/actual-runtime authority remains absent.

## Exact existing API seams

Pinned SM147 is `9dab3d6f643e926a340c391ea30968e940390dec`, as recorded by the unchanged adjacent async-context source audit. `JS::JobQueue` exposes `getHostDefinedData`, `getHostDefinedGlobal`, and `enqueuePromiseJob(...,hostDefinedData)`. Captured empty context must be a real non-null resource, not the optimized-out sentinel.

Current `runtime/engine.cpp::init_js` calls `js::UseInternalJobQueues` before `JS::InitSelfHostedCode`. The default native microtask preference is true. The experimental ALS path will select the real supported `JS::Prefs::set_use_js_microtask_queue(false)` before any application registration and install a custom legacy JobQueue. Normal and finalizer checkpoints remain `js::RunJobs`, including its real `JS::ClearKeptObjects` behavior; tick/event ordering is not replaced.

The actual public dispatch setup spelling is `JS::InitDispatchsToEventLoop`. The first proposed profile has an explicit **no SM off-thread/delayed-dispatch feature contract**, rather than silently omitting the old internal queue's `offThreadPromiseState.internalDrain`. Its dispatch callbacks must refuse one-way without GC or JS from another thread, and surface attempted unsupported dispatch at the next checkpoint. Promise jobs, embedding tasks and ordinary synchronous native FS work returning Promises are distinct from this unsupported SM background facility. A future complete dispatch implementation or a justified small guest-SM drain hook needs separate Source/build validation; no host changes are proposed.

It copies enabled bindings into a distinct resource at creation, retaining store values by identity. SM explicitly treats metadata callback/table allocation failure as fatal. The builder must be installed in both content/initializer realms, whose existing setup shares a compartment; no new realm or fake global carries ALS state. Unknown cross-compartment/unknown private job layouts remain unsupported until explicitly handled.

The existing resource-model-v3 is relevant bounded evidence, not an implementation to import or rerun. Real result Promise creation, thenable assimilation, optimized native/await jobs and plain-object species need distinct selection. ## Store and lifetime rules

`ResourceStore` holds its current/root resources in real PersistentRooted objects. Resource slot0 points to a private list; each node holds branded state, store and next. Slot1 retains the request owner root (a fresh root owns itself). Reserved slots receive ordinary GC tracing. Capturing a child copies only currently enabled bindings and never shares mutable nodes. This preserves disable/re-enable, captured-disabled emptiness and same-resource enterWith mutation. Restoring one ALS binding changes an already-present node without allocating, so it preserves another ALS instance's mutations and cannot replace an original thrown value. Resource invocation has a rooted RAII scope that installs/restores both current resource and request owner, including after initial JS return via subsequent child jobs.

The proposed finite limit is256 bindings per resource; overflow is a coded RangeError. It is a profile deviation, not Node's limit. Overall live cells/jobs remain subject to the engine heap and a forthcoming explicit queue cap. Root resources can retain disabled bindings, as required for old live resources to reveal stores after re-enable; request-root lifetime and release must be deliberate.

Static bind/snapshot capture a native resource once and reuse its cell. Full AsyncResource IDs/hooks/destroy semantics and deprecated bound.asyncResource descriptors are deferred. The proposed schema-valid manifest uses `sm-node-22.14.0-m1.0`, exact7named+default inventory and63 frozen provider numbers read from pinned Node22 metadata. These numbers are inventory metadata, NOT evidence that those guest providers exist. Deferred callable/constructor APIs throw explicitly. The metadata reader created no explicit ALS instance or workload; its counters qualify that program's actions, not all Node-loader internals.
