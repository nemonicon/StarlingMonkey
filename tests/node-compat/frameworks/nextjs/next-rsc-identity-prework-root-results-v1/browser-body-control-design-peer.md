# Chrome body-control design: independent Source peer

The agreed narrow mechanism is Source-feasible: finish the existing non-browser prework, create one fresh Chrome context, fulfill one synthetic same-origin `/actions` document, remove that route, then call the page's real `window.fetch` with the captured 391-byte body and consume `Response.arrayBuffer()`. It changes the consumer and document setup; it does not reproduce the original React/form/navigation workload or repair its failed strict result.

Review basis is Root's agreed proposal and the pinned APIs below. R's standalone `browser-body-control-design.md` was not present at this cutoff. This note therefore authenticates neither an absent design file nor future implementation bytes; the new client, actors and Root wire require their separate Source peer. All future outcomes remain unobserved here.

The smallest implementation contract is:

1. Use the existing explicit Chrome executable and Playwright package in a fresh context with service workers blocked, no user profile, extensions, cookies, HTTP credentials or application scripts. Add no guest capability or host service. Preserve the original strict worker unchanged.
2. Restrict bootstrap fulfillment to exactly one main-frame navigation GET at the issued origin's `/actions` URL. Fulfill static inert HTML with no external resources, do not fetch an application document, and record that the document was synthetic. Await removal of the route before the POST. Assert the committed document URL and `location.origin` equal the declared URL/origin. `page.setContent()` on an initial `about:blank`, or adding a base URL, is not an origin-establishment substitute.
3. Execute `window.fetch` through `page.evaluate`, not Playwright's API request context. Construct a `Uint8Array` from the retained body bytes, keep the multipart boundary and Content-Type exact, remove the public correlation header, and do not regenerate FormData or trigger React/router/form submission. An appropriate explicit script-header allowlist is Accept, Accept-Language, Content-Type, Next-Action and Next-Router-State-Tree. Record the selected fetch mode, credentials, referrer, cache, redirect and abort policies, including any differences from the captured request.
4. Do not forge the thirteen browser-managed captured header fields through context-wide extra headers, CDP overrides or request interception. Retain actual observed request headers/body and list differences or unavailable fields. Source strings alone do not prove the on-network request. Use a single admitted POST/method/URL and actual request-object bookkeeping; CDP IDs and NetLog IDs remain local, separate namespaces.
5. Keep the document/context live through fetch settlement, the attempted arrayBuffer read and an independently observed loading terminal. Record fetch headers/status/type/redirected separately from body fulfillment/rejection and CDP loadingFinished/loadingFailed. A rejected read has no returned body prefix: publish null/unavailable bytes and its error, never fabricate raw data from byte counts. Known failed observation can be complete as an observation while remaining semantically failed; overflow, missing terminal or cleanup/publication uncertainty is a separate collection failure.
6. Keep the whole operation under the declared absolute deadline. Handle both fulfillment and rejection immediately, abort on timeout, and record whether abort came from the control. Preserve normal-close/outer-owner cleanup gates and durable result/receipt/body publication before the terminal summary. No navigation, automatic redirect traversal, retry or replacement follows from a failed read.
7. Treat the 4 MiB arrayBuffer check as a post-read acceptance/publication bound. It does not bound allocation before fulfillment. Transporting base64 through the evaluation channel also allocates memory; publish the returned bytes as a separate body artifact and keep its descriptor in the bounded result. If a hard incremental allocation bound becomes necessary, that requires a separately declared reader experiment rather than calling it arrayBuffer-only.
8. A positive bounded result needs the prework predicate, admitted request metadata, HTTP200/unredirected response, actual absent Content-Encoding, fulfilled browser body with the required RSC markers, successful network terminal, durable body/result/receipt and known normal cleanup. Record browser errors rather than waiving them. Such a result establishes none of the original strict UI contract, host canonical completion, private instance identity, cancellation cause, harmlessness or reliability.

The Fetch Standard classifies Host, Connection, Content-Length, Origin, Referer and Accept-Encoding, plus Sec-/Proxy-prefixed names, as forbidden script request headers. Request-guard validation can discard them. Its body-consumption algorithm fully reads before creating an ArrayBuffer; fulfillment is a browser body-consumer observation, not a wire capture. These are normative constraints, not an audit of the shipped Chrome implementation. Source consulted: [immutable Fetch snapshot 59afe349, forbidden headers](https://fetch.spec.whatwg.org/commit-snapshots/59afe349913d56898c947576216f1c2579308be7/#forbidden-request-header) and [consume body](https://fetch.spec.whatwg.org/commit-snapshots/59afe349913d56898c947576216f1c2579308be7/#concept-body-consume-body), read 2026-11-08; no external Source artifact was retained.

The pinned Playwright Source makes the bootstrap qualification concrete. In `coreBundle.js` lines 25126–25144, setContent uses document.open/write/close. Lines 37451–37474 enable protocol Fetch for all URLs and disable the network cache while routing is active; a narrow route matcher alone does not exempt the POST from that infrastructure. Awaited route removal before the POST is therefore material. Extra-header setting uses Network.setExtraHTTPHeaders at 37476–37489, which is a different mechanism from normal page fetch and must not be used to claim script-header fidelity.

Network completion needs an independent terminal record. In `coreBundle.js` lines 14465–14559, response.body races page closure, waits the finished promise, then retrieves protocol body bytes. Lines 37714–37756 resolve that promise for both loadingFinished and loadingFailed. Lines 37797–37811 retrieve CDP body data and have no safe-GET refetch fallback for POST. Thus a finished-promise settlement alone is insufficient. The current strict worker already independently records requestfailed/body/sizes/finished outcomes and closes only through its unchanged lifecycle; the new control must preserve failures without claiming it executes those original two functional tests.
