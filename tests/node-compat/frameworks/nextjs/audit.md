This is a source/dependency audit for the reusable Next.js experiment, inspected on 2026-11-05. It is not an application, build, bundling, component, HTTP or browser result. No runtime capability or production acceptance changes follow from it.

The first useful distinction is between compiling the application on stock Node, deploying the genuine generated Next standalone server, and running bounded library/application slices in Wasm. The current runtime can exercise the third category; source inspection identifies real barriers to the full server. Actual attempts must preserve the first observed failure rather than turn these inferences into claimed runtime results.

The existing Node toolchain is pinned to22.14.0; the current fixture selects Next16.4.5 and matching React/ReactDOM19.3.1. Cached Next registry metadata and the current official documentation both identify Next16.4.5; its recorded engine requirement is Node>=20.9.0. Its peer range accepts React18.2/19, while the cached ReactDOM19.3.1 package itself requires React^19.3.1. The installed TypeScript cache also contains React18.3.1, which is a separate artifact and must not silently replace the fixture pair. [Next installation](https://nextjs.org/docs/app/getting-started/installation)

The npm content cache contains React/ReactDOM19.2.0 and19.3.1 tarballs. The19.3.1 bytes were read and their SHA512/internal package versions checked against the cache records. No Next tarball or installed Next package was found in the initially scanned `/private/tmp/starling-node-compat`, npm cache keys and TypeScript-cache roots; a Next metadata blob was present. This is a bounded cache observation, not a global absence claim, an installation result or authority to trust a mutable cache without the experiment's lock/integrity record.

Two package facts are particularly useful for targeted failures. React19.3.1's `index.js` chooses production/development through `process.env.NODE_ENV` and uses relative CommonJS requires. ReactDOM19.3.1's `server.browser.js` and `server.edge.js` are also CJS selectors. Its Node server implementation requires `async_hooks`, `crypto`, `stream` and `util` in addition to React/ReactDOM. Its browser and edge implementations require only React/ReactDOM, but they still hit the current CommonJS bundler policy. The bare `react-dom/server` export defaults to the Node file in the package map; select an explicit declared browser/edge entry for a distinct diagnostic rather than assuming neutral resolution selects one.

The cached browser production renderer unconditionally constructs MessageChannel at module evaluation (member `package/cjs/react-dom-server.browser.production.js`, line135). No MessageChannel definition was found under this repository's builtins/runtime/include. This is a source-inferred later import boundary after CommonJS packaging, not an observed guest error. The edge production renderer avoids that constructor, uses queueMicrotask/Promise and TextEncoder, and constructs byte ReadableStreams with highWaterMark0. It is therefore a useful separate real-library probe. Actual native Web Streams and Promise-drain behavior still require execution; importing the selected `node:stream/web` facade does not replace the global constructor used by React. [React server API distinctions](https://react.dev/reference/react-dom/server)

Next's standalone output is a traced Node deployment directory, not one universal browser/worker bundle. `next build` creates `.next/standalone/server.js` plus traced dependencies; `public` and `.next/static` are not copied there automatically. A real standalone baseline must include those assets and any traced fixture file before launching the generated server. Keep the tracing manifests and generated server bytes, then attempt that entry unchanged in the profile bundle/component pipeline. [Next standalone output](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)

Node filesystem access, server sockets/http, process/env/stdio, runtime file loading and request async context remain distinct blockers after bundling. `node:http`, `node:fs`, `node:net`, `node:process`, `node:async_hooks`, `node:module` and full `node:crypto` are not admitted by the current native profile. Filesystem preopens or WASI HTTP being present elsewhere do not create Node module/API compatibility. Next's default server runtime has all Node APIs; its Edge runtime is a different limited API surface with Next-specific AsyncLocalStorage support, not a guarantee that arbitrary Next Node output runs on any Web-API engine. [Next runtime reference](https://nextjs.org/docs/app/api-reference/edge)

| Case | Real input/oracle | What a successful observation would establish |

| React element / nonstreaming SSR | The same React19.3.1 pair, production selection explicit and recorded | Separate element creation, ReactDOM string renderer and edge renderer stages. A controlled CJS bundler extension, if introduced, must retain native admission and be reported as new packaging tooling, not a new runtime API. |
